# Проект: CRDT-Engine — Распределенный Real-Time Collaborative Engine

### 1. One-Liner / Краткое резюме

Масштабируемый распределенный движок реального времени для совместного редактирования документов на базе **CRDT** (Conflict-free Replicated Data Types) и **Go**, спроектированный по принципам чистой архитектуры с синхронизацией нод через **Redis Pub/Sub** и протокол **WebSocket**.

---

### 2. Ключевые архитектурные вызовы (System Design & Challenges)

1. **Строгая сходимость без централизованных блокировок (Strong Eventual Consistency):**
* **Проблема:** Традиционные подходы (OT — Operational Transformation) требуют центрального координатора и сложны в масштабировании.
* **Решение:** Реализация бескомпромиссных математических структур CRDT:
* **Fugue Algorithm (Sequence CRDT)** для посимвольного текстового редактирования с корректной обработкой интервалов и предотвращением interleaving (перемешивания правок пользователей при параллельном вводе).
* **LWW-Register (Last-Write-Wins)** для метаданных документа (название, свойства).
* **G-Set & 2P-Set** для коллекций (теги, участники).
* **Vector Clock (Векторные часы)** для частичного упорядочивания и отслеживания причинно-следственных связей (causal consistency).




2. **Горизонтальное масштабирование и межсерверный синк (Multi-Node Coordination):**
* **Проблема:** Пользователи одного и того же документа могут подключаться через WebSocket к разным физическим нодам приложения.
* **Решение:**
* Реализован паттерн **Hub / Broker-Worker**.
* Интеграция шины **Redis Pub/Sub** для широковещательной рассылки дельт/операций между экземплярами сервиса.
* Применение пула воркеров (`internal/worker/pool`) для асинхронной десериализации, валидации и применения дельт без блокировки сетевого цикла чтения WebSocket.




3. **Сетевая оптимизация и Ingestion Flow:**
* Спроектирован конвейер обработки входящих операций: `WS Ingestion -> Worker Pool -> Engine Apply -> Redis Publish -> Peer WS Broadcast`.
* Идемпотентность применения операций гарантируется семантикой CRDT: дельты и состояния коммутативны и ассоциативны, повторная доставка не ломает консистентность.



---

### 3. Архитектура и System Analysis (C4 & ADR)

* **Clean / Hexagonal Architecture:**
* `pkg/crdt` — изолированное ядро без внешних сетевых зависимостей (чистые структуры данных и алгоритмы, покрытые свойствами математической сходимости).
* `internal/usecase` — сценарии синхронизации и оркестрация жизненного цикла документа (`sync.go`, `document.go`).
* `internal/websocket`, `internal/redis`, `internal/repository` — инфраструктурные адаптеры.


* **Архитектурный анализ и документация:**
* **C4 Model:** Полный комплект диаграмм на PlantUML/Structurizr DSL: Context, Container, Component.
* **ADR (Architecture Decision Records):**
* *ADR-0001*: Выбор Go для конкурентной обработки сетевых соединений (goroutines/channels) с предсказуемым GC.
* *ADR-0003/0004*: Абстракция интерфейса `CRDTNode` и выбор примитивов (Fugue, LWW, Vector Clocks).
* *ADR-0006/0007*: Разделение сетевого транспорта (WebSocket) и межсерверного транспорта (Redis).

### 4. Стек технологий

* **Язык:** Go (микросервисная архитектура, каналы, `sync.RWMutex`, горутины).
* **Транспорт & Сеть:** WebSockets (duplex real-time client connection), Redis Pub/Sub (inter-node pub/sub).
* **Архитектурные паттерны:** Clean Architecture, Worker Pool, Pub/Sub, Repository Pattern, CQRS-lite.
* **Проектирование:** C4 Model, Architecture Decision Records (ADR), Mermaid/Sequence Flow.
* **Инфраструктура:** Docker, Docker Compose, GitHub Actions CI, golangci-lint.

### 5. Что сказать на System Design секции (Talking Points)

* **Почему CRDT, а не OT (Google Docs)?**
*Ответ:* OT требует строго единого источника правды (single sequencer) для трансформации операций. CRDT децентрализован, масштабируется горизонтально «из коробки» и идеален для P2P или распределенных edge/multi-region топологий, так как узлам не нужно согласовывать порядок через блокировки.
* **Как решали проблему гонок (Race Conditions) внутри ноды?**
*Ответ:* Изоляция работы над внутренним деревом Fugue через мьютексы внутри слоя движка + буферизованные очереди/Worker Pool, распределяющие задачи по хешу ID документа (`shard by document_id`), исключая контеншн между разными документами.
* **Как тестировалась распределенность?**
*Ответ:* Написан e2e/интеграционный сценарий с запуском двух независимых виртуальных нод (`two_nodes_test.go`), соединенных через Redis, с проверкой полной идентичности состояния документов при параллельном вводе данных в разные ноды.
