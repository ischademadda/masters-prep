### Проект 1: Archon — AI-Native Source of Truth & Architecture Platform (Диплом)

> **Статус (октябрь 2026):** спроектирована архитектура (7 ADR) и начат базовый каркас. Ниже — целевой дизайн, а не готовые результаты; метрики — это NFR и цели, которые предстоит измерить.

Archon — облачная enterprise-платформа (Managed SaaS), выступающая AI-native Source of Truth для архитектуры распределенных систем и микросервисов компании. Миссия платформы — Zero Drift: непрерывная синхронизация проектной документации с реальным исходным кодом репозиториев и поставка верифицированного контекста инженерам и AI-агентам (Cursor, Claude Code, GitHub Copilot).

#### Проблематика индустрии
Внедрение генеративного AI в разработку ускорило написание кода, но документация устаревает быстрее изменений. В результате:
* AI-агенты галлюцинируют: при генерации межсервисных вызовов и рефакторинге агенты опираются на устаревшие спецификации, создавая циклические зависимости и ломая продакшн.
* Архитектурный дрейф (Spec Drift): реальная топология сервисов расходится со схемами уже через 2 недели после релиза.
* Высокая стоимость аудита: понимание радиуса поражения изменений (Blast Radius / Impact Analysis) требует ручного чтения сотен репозиториев.

#### Архитектурное решение и внешние каналы (Context-as-a-Service)
Сложность системы скрыта за 5 внешними интерфейсами:
1. MCP-сервер (Model Context Protocol): сетевой шлюз для AI-ассистентов в IDE. Инструменты get_service_contract (выдача актуального DTO/OpenAPI без вычитки чужих репозиториев) и validate_dependency (проверка слоев и отсутствия циклов перед кодогенерацией). Цель — сократить расход токенов в контекстном окне и не давать агентам опираться на устаревшие спецификации.
2. Веб-портал (React / LikeC4): интерактивная навигация C1 (System Context), C2 (Containers/Services), C3 (Components). Монитор расхождений (Spec-Drift Monitor) с точными пруфами из строк кода. Assurance Inbox для принятия архитектурных решений тимлидами.
3. Docs-as-Code Engine & Git Sync (PR-бот): автогенерация файлов AGENTS.md, .archon/ и карточек сервисов через Pull Request'ы. PR-бот комментирует архитектурные изменения и блокирует мерж при нарушении зависимостей.
4. Public API (REST / GraphQL): CI/CD Quality Gates для блокировки сборки при критическом архитектурном дрейфе.
5. Чат-бот (Slack / Telegram / Mattermost): быстрые ответы на вопросы инженеров о владельцах и методах API с обязательным провенансом (ссылками на строки и коммиты).

#### Системные решения и R&D
* Декомпозиция фабрики знаний: 17 ортогональных модулей упакованы в 3 сборочные единицы (archon-core-service на Kotlin, archon-ai-service на Python, archon-portal на TypeScript/React) под управлением Temporal Polyglot Workflows (ADR-0007). Цель — сохранить строгую изоляцию бизнес-логики без операционного оверхеда 17 отдельных сервисов.
* Проектирование мультитенантного Knowledge Graph: проведено сравнение графовых СУБД. Выбран PostgreSQL 16 + Apache AGE с изоляцией Graph-per-Tenant (схемы ag_catalog). NFR: обход графа на глубину 4 для Impact Analysis <100 мс — предстоит проверить бенчмарком.
* Гибридный конвейер Code-to-Architecture:
  - Фаза 1 (детерминированная): синтаксический анализ AST через Tree-sitter извлекает классы, контроллеры, DTO, вызовы клиентов.
  - Фаза 2 (семантическая): LLM-анализ бизнес-контекста и динамических потоков. Спроектирован File Selector агент, анализирующий только структуру каталогов, чтобы резко сократить объём входных данных для LLM.
  - Правило Proof-of-Truth: каждое ребро графа обязано содержать массив evidence_files (путь к файлу, диапазон строк). Связи без проверяемого подтверждения в исходном коде отсекаются валидатором.
* Архитектурные решения (ADR): разработано 7 Architecture Decision Records (ADR-0001 — ADR-0007), зафиксировавших ключевые развилки (Docs-as-Code, изоляция тенантов в Apache AGE, упаковка процессов в 3 сервиса) до начала реализации ядра.

### Проект 2: OmniSearch Engine — Мультимодальный RAG-видеопоиск (R&D, обмен опытом с Газпром Восток Нефть)

OmniSearch Engine — on-premise мультимодальная RAG-система семантического поиска по корпоративным видеоархивам. Система принимает видеопотоки и архивы, автоматически транскрибирует речь, извлекает информативные кадры, формирует векторные эмбеддинги и позволяет находить точные временные отрезки по текстовому описанию на естественном языке.

#### Архитектура и реализация
* Разделение на Control Plane и Compute Plane:
  - Control Plane (Backend API на Kotlin Ktor): прием запросов клиентов, управление правами доступа, оркестрация жизненного цикла видео, генерация presigned URL для безопасного стриминга из MinIO S3, хранение реляционных метаданных в PostgreSQL.
  - Compute Plane (Go Video Engine + Python ML Engine): Go-воркеры выполняют эффективное извлечение аудио и нарезку ключевых кадров через FFmpeg/GoCV без лишнего расхода памяти. Python FastAPI ноды запускают инференс Whisper (speech-to-text) и CLIP (multimodal frame embeddings).
* Векторный поиск: хранение и индексация векторов в Qdrant с фильтрацией по метаданным (длительность, дата, теги объекта).
* Конечный автомат (FSM): спроектирован надежный конечный автомат состояний видео (Uploaded -> Audio Extracted -> Transcribing -> Frame Extraction -> Vectorizing -> Ready -> Failed), обеспечивающий real-time статус обработки и корректную обработку сбоев.
* Применение: система проектировалась под сценарий мониторинга охраны труда и производственной безопасности на удалённых объектах; по этому сценарию был обмен опытом со специалистами Газпром Восток Нефть (внедрения не было).

### Проект 5: CRDT-Engine — Распределенный Real-Time Collaborative Engine (Solo Open-Source)

CRDT-Engine — масштабируемый распределенный движок совместного редактирования документов реального времени на Go со Strong Eventual Consistency без использования централизованных блокировок.

#### Архитектурные вызовы и решения
* Математическая сходимость без OT: отказ от централизованного координатора (Operational Transformation) в пользу CRDT. Реализован Sequence CRDT на базе алгоритма Fugue для посимвольного ввода без перемешивания правок (interleaving). Для метаданных применен LWW-Register, для тегов и участников — G-Set и 2P-Set, для причинно-следственного упорядочивания — Vector Clocks.
* Горизонтальное масштабирование нод: спроектирован паттерн Hub / Broker-Worker. Межсерверная синхронизация дельт между физическими нодами реализована через шину Redis Pub/Sub.
* Ingestion Flow и конкурентность: конвейер WebSocket Ingestion -> Worker Pool -> Engine Apply -> Redis Publish -> Peer Broadcast. Изоляция операций по хешу document_id исключила взаимные блокировки при параллельной работе с разными документами.
* Верификация: разработан e2e-тест распределенной синхронизации с запуском двух независимых виртуальных нод, соединенных через Redis, подтверждающий побитовую сходимость состояния при конкурентном вводе.
